# Version tracking

Binspector follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).
This file records what changed at each version and why, so the reasoning behind a
version bump does not live only in commit messages.

## 5.3.0

**Bump reason:** MINOR. Additive, with one caveat a pipeline owner has to know about: a digest
mismatch is a critical posture finding, so `--fail-on critical` can now trip on something that never
produced a finding before. Nothing existing changed meaning, and both new states default to "not
established" so a saved report loads without inventing a claim.

**Why this was the right next thing.** 5.0.0's signer attribution was an identity claim with nothing
behind it, and the report said so. That honesty was a floor, not a resting place: a hostile binary
could self-sign as anyone and the tool printed the name. Two checks close it. The digest says the
bytes were not changed after signing. The chain says the certificate that signed them was itself
issued by the next one up, cryptographically rather than by a matching name string.

**The range walk is local for the same reason the Mach-O bind walk is.** goblin's
`authenticode_ranges()` raw-indexes `size_of_headers`, `pointer_to_raw_data + size_of_raw_data`, and a
certificate-table subtraction that underflows. Three reachable aborts. Reimplementing it is only
defensible if the result is *the same*, so the plan is compared against goblin's iterator over all
441 real images: agreement byte-for-byte, zero panics, zero declines.

**The strongest evidence that the ranges are right is not the 262 verified images.** It is that
flipping one byte inside the certificate table leaves an image `verified` while flipping one byte in a
section turns it to `mismatch`. The first says the exclusion is implemented; the second only says
hashing works. A test suite that checked only the second would pass with the exclusions missing.

**`partial` exists because the obvious design would have reported a lie.** With four states, 260 of
262 signed images came out `unverified`, which reads as "nothing was checked". What actually happened
is that every certificate in the file verified and the root is not in the file, because Authenticode
omits it. Those are different facts and a reviewer acts differently on them, so they are different
states. Finding this needed running on real data; no unit test would have surfaced it.

**SHA-1 is verified rather than refused, and that is a deliberate security judgement.** Refusing it
would report a legitimate older Microsoft chain as unverifiable, which a reader cannot distinguish
from a forged one. Indistinguishability is the defect. Verifying what an issuer signed is a statement
about the signature, not an endorsement of the algorithm.

**Two things the tool will never claim, and the reasons are structural rather than scheduling.** It
will never say "trusted": no pure-Rust code-signing root store exists, `webpki-roots` is Mozilla's TLS
list, and Microsoft's anchors are in a CTL with no crates.io mirror. So the anchor fingerprint is
printed and the reviewer compares it against a published thumbprint. And it will never check
revocation: OCSP and CRL fetch a URL out of the hostile certificate, which is attacker-controlled
outbound traffic, an SSRF-shaped channel and a scan-detection beacon at once. That is strictly worse
than `--reputation`, which sends a hash to an endpoint the user chose, and it fails the same test the
AI component failed in 3.0.0.

**Cost.** Four new pure-Rust dependencies, `rsa`, `p256`, `p384`, and `signature`, and the digest is a
full pass over each signed image's bytes. Measured on the bundle: 6.2 seconds to 7.0, about 13%,
rather than the 20% estimated, because only 262 of 441 images are signed.

## 5.2.0

**Bump reason:** MINOR. Additive on every surface: new analysis for two formats that were parsed
but not read, new posture ids that cannot collide with the PE ones, and a roll-up that changes
which occurrences are *listed* in the human reports without changing any count a pipeline reads.

**The justification is a structural zero, not a feature gap.** `Confidence::Import` is the tool's
strongest evidence tier, and it was reachable only through a PE import directory, so
`definitive_hits()` returned zero for every ELF and Mach-O binary by construction. A tool that
reports "import-backed occurrences: 0" on a Linux binary is not quietly weaker there, it is
reporting a number that can never be anything else.

**Correction to an earlier claim made in planning.** I said twice that the `imports_known` guard
skips *three* evidence rules for non-PE members. It is read in exactly one place and gates one
branch of one rule. The evidence-side payoff of Unix imports is therefore narrower than claimed,
and the import-hit-path payoff is larger. The work stands on the latter.

**Two goblin traps, both avoided deliberately.** `Sym::is_import()` is the wrong ELF predicate: it
tests binding plus a zero value rather than `SHN_UNDEF`, so it false-positives on defined symbols
at address zero and false-negatives on common blocks, and there is a second free function of the
same name that omits weak bindings. And `MachO::imports()` returns empty on any image using
`LC_DYLD_CHAINED_FIXUPS`, which goblin recognises and never interprets.

**The chained-fixups reader came out of testing, not planning.** The plan's fallback was the
`LC_SYMTAB` undefined externals, and that fallback works: it finds the same names. What it cannot
do is say which library any of them came from, because the dylib ordinal lives in `n_desc` and is
not exposed. Probing a freshly linked binary showed the consequence: 1,055 imports across eight
system binaries, none attributed. Reading the chained import table directly attributes all 1,055,
and that attribution is what the loader and IPC narrowing depend on to say "imports
`CreateNamedPipeW` from `KERNEL32.dll`, nothing from `ADVAPI32.dll`'s token family".

**`exec-heap` was specified wrong and was narrowed.** As planned, the absence of
`MH_NO_HEAP_EXECUTION` would have read as "executable heap" on every x86_64 and arm64 image, which
is every current macOS binary including Apple's own signed system ones. The flag affects the i386
ABI only. It is gated on `cputype == CPU_TYPE_X86`, so in practice the rule will essentially never
fire, which is the correct answer: a Mach-O heap finding with real reach needs a different signal
than this flag.

**ELF `nx` is deliberately not scoped to executables, where the three Mach-O flags are.** The
kernel reads `MH_PIE`, `MH_ALLOW_STACK_EXECUTION`, and `MH_NO_HEAP_EXECUTION` from the main
executable's header, so none of them says anything about a dylib. But the ELF loader ORs
`PT_GNU_STACK` across every object it maps, so one shared library with an executable stack makes
the whole process's stack executable. That is the rule's best case, not an exception to it.

**Fuzzing the new path changed the design, and this is the part worth remembering.** The plan read
imports through `MachO::imports()`. Twenty thousand mutations of `/bin/ls` found a reachable panic
at iteration 63 and a 3.9-second execution from a 120-byte opcode stream: goblin raw-indexes
`libs[symbol_library_ordinal]`, and it honours an attacker-chosen ULEB repeat count by pushing one
entry per repetition. The first attempt at a fix was a `catch_unwind` with a scoped panic hook,
which was the wrong shape: it addresses the crash and not the allocation, and it swaps a
process-wide hook to stay quiet. The walk is local now, and the thing that makes it bounded is not a
cap but a question: a repeat count binds the same symbol at successive addresses, so for an import
list it says nothing and is discarded. **Safe was the easy half; faithful needed a differential.**
Name-for-name agreement with goblin over 46 system binaries found two real defects that every unit
test had passed: `BIND_OPCODE_DONE` separates lazy entries rather than ending the stream, and a fat
binary's linkedit offsets are slice-relative where goblin's slicing makes them look absolute.

**Scoped out, with the reason recorded.** Mach-O hardened runtime and entitlements. `CS_RUNTIME` is
a flag on the `CodeDirectory` blob inside the `CSMAGIC_EMBEDDED_SIGNATURE` SuperBlob, and goblin
exposes only that blob's offset and size. Reading it means a from-scratch big-endian SuperBlob
parser over attacker-controlled bytes, which is larger and riskier than the rest of this work put
together. So the tool reports whether a signature is *present* and claims nothing about what it
asserts.

## 5.1.0

**Bump reason:** MINOR. Additive: several targets and directory scanning, with single-target
output unchanged.

**The refactor was chosen for blast radius, not elegance.** The plan called for hoisting the
banned list, the matcher, and the accumulators into a shared engine so N targets paid the setup
once. Measuring the actual cost changed the decision: the list is embedded (no file I/O) and the
automaton covers 226 patterns, so per-target setup is sub-millisecond, while the hoist would have
restructured a 850-line module that 445 tests depend on. `run_many` merges per-target reports
instead, `run` delegates to it for one target, and the suite needed no edits.

**Three defects came from running it on the real dependency tree, and none would have been caught
by a test.** Every table row was flagged, because the routine low-confidence disclosure counted as
a per-target warning; a marker that fires on all ten rows says nothing. Tail truncation rendered
`arm64/Microsoft.WindowsAppRuntime.2.msix` as `~64/...`, which a reader cannot tell from
`x64/...`, so truncation now keeps both ends. And two rows could still collapse to the same string
where names differ only in a middle segment, which a `#n` suffix now prevents, because a duplicate
row in a security report is a defect rather than a cosmetic issue.

**The manifest digest is the one piece of design worth remembering.** A set of files has no file
hash. Filling `sha256` with a digest of concatenated bytes would be meaningless and would look
authoritative; leaving it empty would lose a stable identifier for the run. A `sha256sum`-style
manifest over `"<sha256>  <label>"` lines is reproducible, checkable by hand with a standard tool,
and obviously a manifest rather than a file hash. `md5` and `sha1` are cleared, because there is no
equivalent convention for them and a half-filled set of hash fields invites misreading.

**Symlinks are handled structurally rather than defensively.** Using `DirEntry::file_type`, which
is `lstat`-based, means a recursion loop cannot happen, as opposed to being detected by visited-inode
bookkeeping that could have a gap. An explicitly named path is still followed, which is the same
distinction `find -H` draws: naming a path is an instruction, discovering one is not.

**Deliberately rejected.** `--dump` across several targets, which would need a spool per target
and would produce millions of strings per target anyway, and `--split` to stdout. Both fail with a
message saying what to do instead rather than silently doing something partial.

## 5.0.0

**Bump reason:** MAJOR. Severity values change, occurrence counts drop, `--fail-on` can trip on
new grounds, and four model fields are renamed. Any of those can change a pipeline's exit code.

**This release came from an adversarial review, not a feature list.** Three agents adjudicated
301 findings from a 4.2.1 scan of the reference bundle and refuted or disputed roughly 239 of
them. Its central charge was that the tool computes a `confidence` field and then ignores it, so
an import-table resolution and an incidental substring in a UI resource string get byte-identical
severity. I reproduced all ten of its numbered defects against 4.4.0 output before changing
anything, which is the part that made the work tractable: each defect became a number to move.

**Modelling the fix first was worth more than any amount of design.** Before writing code I
applied the proposed rules to an existing JSON report in Python and measured the outcome: 331
occurrences to 239, critical+high to 63, and every surviving critical import-backed. That last
property is the review's own claim, that everything it refuted was `symbolic` or `exact` and
everything it sustained was `import`, and it fell out of the rules rather than being asserted by
one. Knowing the target numbers in advance turned verification into a check rather than a
judgement.

**Three rules exist only because a subagent pushed back.** The one that mattered most: requiring
import backing for an ordinary-English name would have dropped every `system()` call in a native
ELF or Mach-O binary, because `Confidence::Import` is only derivable from a PE import directory.
That is a coverage loss wearing the costume of precision, and on a tool that advertises Linux and
macOS support it would have been a serious regression shipped as an improvement. The same review
caught that Itanium mangling puts a length digit before the token, so the OpenCV false positive
this release fixes on Windows would have returned from a Linux build, and that `IsBad*Ptr` was
misfiled as a harmless read when it in fact suppresses the guard page that would otherwise turn
a bad pointer into a clean crash.

**Two refinements came from running it, not reading it.** A PE with no import directory at all,
which is any packed or resource-only image, offers no evidence of absence either, so
`imports_known` had to mean "a usable table was read" rather than "the PE parsed". And
`--first-party` matched the full provenance chain on the first attempt, which always begins with
the scanned file's own name, so `^PSExpress` attributed all 243 images of
`PSExpress_6.9.0.0_x64.msixbundle` to first-party. Both were caught by looking at real output on
the reference bundle rather than by a test.

**Mitigations as findings is the item with the best ratio in the whole release.** The data was
already collected for all 441 images and thrown away into prose. ASLR disabled on three images is
confirmable from metadata alone, needs no call site, no disassembly, and no source access, and is
fixed by one linker flag. It is a better finding than any string match the tool produces, and it
took one new file.

**Signer attribution is the one place I accepted a pre-release dependency.** `cms` 0.3 is pinned
exactly, so the version is reproducible rather than floating. BER parsing is deliberately
refused: `der`'s indefinite-length scanner recurses per nested length, and a crafted blob would
abort the process rather than raise a catchable error, which on a tool whose entire premise is
parsing hostile binaries safely is not a trade worth making. Authenticode mandates DER anyway.

**Deliberately not done.** Signature *verification*. The report states plainly that a signer is
an identity claim with no chain validation, no revocation check, and no hash comparison, because
a hostile binary can self-sign as anyone and a reader who assumed otherwise would be worse off
than with no attribution at all.

## 4.4.0

**Bump reason:** MINOR. New analysis and a feature-default change, both additive. The one
behavioural diff is `system`'s category string.

**The `--format all` bug came from a real run, not a test.** Asked for every format on a
released binary and got six files plus an error. Two causes, and the second is the one worth
remembering: `all` advertised a format the build could not write, and the output loop treated
one writer failing as a reason to abandon the rest. A completed analysis is worth more than a
tidy error, so several formats now degrade to partial output plus a non-zero exit rather than
losing everything after the failure point. The bug had survived because the test named
`format_all_writes_every_file` never actually passed `all`.

**The feature flip was the risky part, so it shipped alone.** CI release-builds six targets
with plain `cargo build --release`, which is why the features were missing from published
binaries in the first place, and turning them on meant every cross target had to compile the
bundled SQLite C amalgamation. `bzip2` and `zstd` were already non-optional and both compile
C, so the risk was lower than it looked, but two empty releases earlier in the 4.x series came
from exactly this class of failure. Pushed on its own, confirmed green on all six targets
including `aarch64-pc-windows-msvc`, and only then built on.

**The loader work is where the judgment went.** The request was to cover dangerous Windows DLL
calls, `LoadLibrary` included. Measuring first showed why that needed splitting: 78 of 441
images import the `LoadLibrary` family, and adding the whole family as findings would have
grown the report by 191 occurrences, 96 of them from `GetProcAddress` and `GetModuleHandle`,
which do not influence search order at all. Worse, `LoadLibrary` with a qualified path is
correct code and the argument is not in the import table, so those findings would have been
inference wearing the costume of evidence. That is precisely the failure 3.0.0 was written to
fix, and it would have been reintroduced in a new form.

So the calls Microsoft's own guidance says not to use became findings, 30 new occurrences, and
the `LoadLibrary` family became a per-image surface with a three-state verdict built from the
three things that are knowable without a disassembler.

**One iteration was needed on that surface.** The first version listed every bare module-name
string and so flagged 27 of 41 images with `KERNEL32.dll` and `api-ms-win-crt-*`, which appear
in nearly every PE because they are in the import directory. Statically imported names, API
sets, and self-references are now excluded, which is what turns the evidence from noise into
`verifier.dll`, `xdpapi.dll`, and `RGB9Rast.dll`: modules an image names but does not
statically import.

**The mitigation column deviates from the plan deliberately.** The plan put `dll_search` in
`Mitigations`. `Mitigations::from_pe` sees only headers, while the verdict needs imports and
strings, so storing it there would have meant a second source of truth kept in sync by hand.
It lives on the loader surface and is rendered as a matrix column instead, which satisfies
"report it the way ASLR and DEP are reported" without the duplication.

## 4.3.0

**Bump reason:** MINOR. Two additive features plus a new default, with no change to existing
behavior or output content.

Both features came out of using the tool on a real 249.6 MiB bundle rather than from a
feature list.

**The scan was opaque while it ran.** It reported 2,967 members, 441 PE images, and 24,196
suppressed occurrences, then printed a result. Nothing showed which decisions produced those
numbers, so when one looked wrong the only route was to add prints and rebuild. The
suppression count was the sharpest case: a reviewer had to trust that 24,196 exclusions were
correct. `-vv` now names the rule behind each one, and the drop-line count matches
`low_confidence_total` exactly.

**A finished report was hard to interrogate.** A 3.2 MB JSON document holding 441 PE analyses
is awkward in `jq`, particularly for cross-cutting questions. The browser exists for those,
not to replace `jq`.

**Design constraint that shaped the verbose work:** the library does not print. Every
`println!` lives in `src/main.rs`, and the scan returns warnings in `Report.warnings`. Rather
than scattering prints through the scan, verbose output is an observer the binary wires to
stderr, which preserved that separation and made the levels testable with a recording test
double.

**An AI component was considered and rejected.** `intel::http` already posts through curl with
secrets on stdin and `intel::creds` already handles keys, so it would have been cheap. But for
internal binaries, sending findings to a hosted model is the same class of disclosure as the
`vt scan` upload deliberately removed in 3.0.0, and the marginal value over pasting a Markdown
report into a chat window does not justify weakening an unqualified safety claim.

**The default output name** is `binspector_output-<YYYY.MM.DD-HH.MM.SS>.<ext>`, which is what
the v1 shell implementation produced, so output from either version sorts together. It is built
from `time` component accessors rather than a format description, which adds no dependency and
cannot fail at runtime. One subtlety cost a test: `Path::file_stem` reads the seconds field of
a dotted timestamp as an extension and truncates it, so the naming strategy is an explicit
enum with an `Append` variant rather than a blanket extension replacement.

**Verified before tagging**, per the process change made after the two empty releases earlier
in the 4.x series: the full local gate, both feature-gated builds, `-v` at every level against
the real bundle, stdout byte-identical at `-vv`, and the browser answering against a real
report. CI green on `dev` before the tag.

## 4.2.2

**Bump reason:** PATCH. Packaging only, with no change to the software.

Found by a question rather than by a test: asked whether the release assets being archives
was intentional, checking the archives revealed that four of the six contained the binary
alone. The Linux job pointed `tar -C` at `target/<target>/release`, where README.md and
LICENSE do not exist, and its `||` fallback chain swallowed the failure. The Windows job
handed `Compress-Archive` only the executable. macOS was correct because that job had been
rewritten separately in 4.1.0, which is exactly why the gap went unnoticed.

The lesson is the same one as the fuzz-harness break: a step that only runs on tags is a
step the ordinary gate never exercises. This time both packaging paths were run locally
before tagging, including the PowerShell block under `pwsh`.

## 4.2.1

**Bump reason:** PATCH. Metadata and documentation only, with no change to behavior.

Two things happened here. The declared license was corrected: `LICENSE` has always been the
GNU GPL v3, but `Cargo.toml` said MIT. That is a metadata fix, not a relicensing, and the
crates this links under MIT and Apache-2.0 are compatible with distributing the whole under
the GPL.

The reference sample was also genericized, in the working tree and in history. The part
worth recording is that renaming the file was not sufficient: the sample's MD5, SHA-1, and
SHA-256 were sitting in the report test fixtures, and a digest identifies a specific file
more precisely than its name does. The exact byte size was the same kind of leak. Both are
now synthetic.

History was rewritten across 14 commits with `git filter-repo`, covering blob contents,
commit messages, and annotated tag messages. The rule ordering mattered: a general
`adobe` rule placed before the specific ticket-URL rule produced a half-rewritten
`jira.corp.vendor.com`, so specific patterns run first.

## 4.2.0

**Bump reason:** MINOR. `--help` renders differently, which is user-visible behavior, and
`usage.md` is a new documented surface. No change to scanning behavior or output.

The 4.1.x line was never published. v4.1.0 and v4.1.1 shipped with zero assets and their
releases have since been deleted; 4.1.2 was held unreleased pending CI, which did come back
green. Their changelog entries stay for history, and 4.2.0 contains all of that work.

The dependency upgrade deserves a note: moving the hash crates to 0.11 changes code that
produces the hashes reputation lookups key on, so it was verified two ways rather than
assumed. The known-answer tests pass, and all three digests match the system `md5` and
`shasum` output byte for byte on a 256 MiB sample.

## 4.1.2

**Bump reason:** PATCH. A build fix, with no change to the software's behavior.

**Two empty releases, one root cause each, and a process failure common to both.**

v4.1.0 failed because the harnesses lived in a crate outside the root gate. v4.1.1 failed
because the fix put them inside the crate but behind features that use the engines'
persistent-mode macros, which need engine runtime symbols at link time. `cargo test
--all-features` therefore could not link on Linux. It linked on macOS, so the local gate
passed again.

The structural fix is to remove the coupling rather than work around it: the harnesses are
plain file-reading programs, which is the mode both AFL++ and honggfuzz already drive
through `@@` and `___FILE___`, and the mode the engine orchestration already emitted.
Nothing in the build references an engine runtime now.

The process failure is mine and is worth recording: both tags were cut on the strength of
`make check` passing, when the failing step was one `make check` did not run. Every CI step
is now run locally before tagging, and a tag is cut only after CI is green on `dev`.

## 4.1.1

**Bump reason:** PATCH. A build fix and a source move, with no change to the software's
behavior.

**What went wrong, and why the local gate missed it.** 4.1.0 added a field to
`container::Limits`. Every constructor inside the crate was updated, but the fuzz
harnesses lived in a separate `fuzz/` crate carrying its own `[workspace]`, which put
them outside everything `cargo test` and `make check` build at the repository root. The
gate passed locally while the harnesses did not compile. CI caught it, and because the
platform build jobs declare `needs: quality`, v4.1.0 published zero assets.

The fix is structural rather than a patch to the one call site: the harnesses are now
`src/bin/fuzz_*.rs`, ordinary binaries of this crate, so a plain `cargo build` compiles
them. `make check` also runs `fuzz-build` now. A library type change can no longer break
them unnoticed.

A second defect surfaced from the same move: `--all-features` enables both engine
features at once, which matched two `main` gates. They are now mutually exclusive.

## 4.1.0

**Bump reason:** MINOR. New formats and a new optional flag, with no change to existing
behavior or output for inputs that were already handled.

This closes the deferral recorded under 3.0.0 and carried through 4.0.0. Nothing Binspector
detects is now left unopened: the single-stream formats decompress, 7z and cab enumerate,
and `--carve` covers embedded data that no directory declares.

The carving work needed two rounds of filtering to be usable, both driven by measurement
rather than assumption. Raw binwalk output on the reference sample was 2,348 signatures
dominated by copyright text and DER hashes, and one of the remaining "containers" turned
out to be a four-byte ZIP magic collision inside a 36 MB DLL. Both are now handled, and
both have regression tests built from the real data.

## 4.0.0

**Bump reason:** MAJOR. `--ignore-case` is removed, so an invocation that passed it now
fails. The positional target also became optional to make room for the `fuzz`
subcommand, so a bare `binspector` with no arguments is now an error rather than a
usage message about a missing file.

The three phases the 3.0.0 roadmap listed separately as 3.1.0, 3.2.0, and 3.3.0 all
landed here. Shipping them behind the breaking removal would have meant three
consecutive tags each breaking the same flag.

### Still deferred

`binwalk` carving and gzip, bzip2, xz, 7z, and cab unpacking remain unimplemented, now
tracked for 4.1.0. The ZIP family still covers every container in the reference sample,
and those formats are detected and reported as a coverage gap rather than silently
skipped.

## 3.0.1

**Bump reason:** PATCH. No change to the software itself. Two CI faults meant v3.0.0
published only 4 of 6 platform assets, so a new tag was needed to produce the complete
set. The aarch64 Linux job had been broken since 2025-10-01 and the x86_64 macOS job
depended on a deprecated runner that never started.

## 3.0.0

**Bump reason:** MAJOR. Two changes break the 2.0.0 contract:

1. Matching is now case insensitive by default, where 2.0.0 was case sensitive, so an
   unchanged invocation can return different results.
2. The no-op `fuzz` subcommand placeholder was removed, so `binspector fuzz` is now read
   as a request to scan a file named `fuzz`.

Separately, results change substantially even where flags did not, because 2.0.0
reported false positives and missed real findings. Any stored baseline must be redone.
Every other 2.0.0 flag still works, with `--ignore-case` and `--json` kept as deprecated
aliases that warn rather than fail.

### Why this release exists

2.0.0 did not work. Verified against a real scan of
`SampleApp_1.0.0_x64.msixbundle` for
an internal tracking ticket:

- All 3 reported findings were false positives. `gets` matched `targetsize`,
  `system` matched `System` and `FileSystem` and `CustomSystemFont`.
- Real coverage was zero. `strcpy`, `strcat`, `sprintf`, `memcpy`, `printf`, and
  `malloc` each returned 0 occurrences in a 256MB Windows application, which is
  impossible. The `.msixbundle` is a ZIP, so the scan only ever saw compressed bytes.

### Changed

- Matching is case insensitive by default. `--case-sensitive` selects the opposite.
- CSV output no longer requires `--matches-only`.
- Reported offsets point at the matched token, not at the containing string.
- Default output is a summary. A full per-string dump requires `--dump`.

### Deferred from this release

- **binwalk carving.** The plan scoped an optional `carve` feature using the `binwalk`
  crate for embedded data in formats Binspector does not parse. The library is confirmed
  usable (`Binwalk::new()`, `.scan(&data)`, `AnalysisResults`, with pure-Rust ZIP and
  inflate extractors), but it was not wired up. The ZIP family covers the containers that
  actually mattered here, and the dependency adds build weight for a capability nothing
  in the verification set needed. Moved to 3.1.0, where PE parsing gives it a clearer
  purpose.
- **gzip, bzip2, xz, 7z, and cab unpacking.** Detected and reported as a coverage gap
  rather than opened. Also 3.1.0.

### Deprecated

- `--ignore-case`: now the default, accepted with a warning so existing command lines
  keep working.
- `--json`: use `--format json`.
- The no-op `fuzz` subcommand placeholder was removed. Real fuzzing lands in 3.3.0.
